# Photobooth

A self-serve photobooth kiosk. SwiftUI, iOS/iPadOS 17+, universal — **iPad
landscape and iPhone portrait** — built to be left alone on a stand at an
event.

The whole UI is a silkscreened hardware panel: white paper, black ink, 4pt
rules, and a real 5x7 bitmap face. Every screen is one or two labelled
modules whose title breaks the top rule, with a value at its right end —
the way a front panel is printed.

```
PhotoboothiPad/
├── Photobooth.xcodeproj          generated by make_project.py — do not hand-edit
├── make_project.py               rescans PhotoboothApp/ and rewrites the project
├── build.sh                      build / run (needs full Xcode)
├── check.sh                      syntax-check every file with no Xcode at all
└── PhotoboothApp/
    ├── App/          entry point, flow shell, Info.plist
    ├── Flow/         one file per screen + the operator console
    ├── Panel/        the design system: module frames, bitmap font, pixel icons
    ├── Camera/       AVFoundation capture + the SwiftUI preview
    ├── Layout/       layout templates (data) and the print renderer
    ├── Printing/     PrinterService protocol + AirPrint and ESC/POS backends
    ├── State/        session flow machine, settings, persistence
    └── Resources/    asset catalog
```

## Building

**You need the full Xcode.** The iOS SDK ships inside it and is not available
as a separate download, so Command Line Tools alone cannot build this.

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
sudo xcodebuild -license accept

./build.sh          # iPad simulator
./build.sh iphone   # iPhone simulator
./build.sh run      # install + launch on a booted simulator
./build.sh device   # a real iPhone or iPad
./build.sh open     # regenerate and open in Xcode
```

To run on a real device you also need a signing team: open the project, select
the **Photobooth** target → **Signing & Capabilities**, tick *Automatically
manage signing* and pick your Apple ID. A free account works — the app then
needs re-signing every 7 days.

Until Xcode is installed, `./check.sh` parses every source file with the macOS
toolchain. That catches syntax errors only — it is **not** a substitute for a
build, and no part of this has ever been compiled.

## iPhone and iPad

One binary, two shapes. `PanelScreen` measures the stage once and publishes
`Panel.Size` (`.compact` below 700pt wide, `.regular` above) through the
environment; every component reads it rather than measuring for itself, because
two views disagreeing about the breakpoint is how a layout goes crooked.

- **iPad** runs landscape. Review and Confirm put the sheet beside its
  controls; layouts are a 3x2 grid.
- **iPhone** runs portrait. `AdaptiveSplit` stacks those two panes; layouts
  become 2x3; the header drops its hatch and badge so the wordmark keeps a
  readable size; the confirm screen shows the three lines a guest is actually
  confirming and leaves sheet size and printer to the operator.

The touch target does not scale. 68pt is the floor on every device — the
drawing gets smaller, the targets do not.

`make_project.py` regenerates `Photobooth.xcodeproj` from whatever Swift files
are on disk. Add a file, re-run it. Object ids are derived from stable hashes,
so an unchanged tree regenerates byte-identically.

`web/` is a **working browser build** of the same booth — same flow, same
layouts, same renderer, same look — for testing on a Mac without Xcode. Serve
it (`python3 -m http.server 8815 --directory PhotoboothiPad/web`) and open
http://localhost:8815; the camera needs localhost, not `file://`. See
[web/README.md](web/README.md).

## The look

Three rules, and everything else follows:

1. **White paper, black ink, heavy strokes.** Every edge is a 4pt black rule.
   No bevels, no gradients, no shadows.
2. **Everything lives in a labelled module.** `PanelModule` draws the frame
   whose top edge *is* the label row — rule stub, name, long rule, value,
   stub. Dashed leaders carry a label to its value (`SpecRow`), which is the
   most characteristic detail in the whole language.
3. **Colour is a fill, never a stroke, and always muted.** Four accents —
   lavender (selection, progress), salmon (destructive, alarm), sage
   (confirmation), slate (neutral). A screen reads black-and-white first.

Type is a real 5x7 bitmap font drawn with `Canvas` (`Panel/PixelFont.swift`),
not a bundled face — for the same reason the icons are drawn: there is no
pixel font on iOS, and the look does not survive a smooth one. The glyph
table is shared verbatim with `web/booth.js`, so the two builds cannot drift.
`PixelText(fits:)` shrinks the cell rather than letting a label overflow.

Photographs and composed sheets sit in `DisplayWell` — the dark panel with the
dashed measurement grid.

## The flow

```
attract → layout → capture → review → copies → confirm → printing → thank you
   ↑                                                                     │
   └────────────────── idle timeout / ✕ on any window ───────────────────┘
```

**Layout is chosen first**, before the camera opens, so the app knows how many
frames to shoot.

**Retake is per-frame.** On the review screen every shot is a button: tap one
to mark it, tap again to unmark. The single retake button then says what it
will actually do — `RETAKE ALL` with nothing marked, `REDO 2 SHOTS` with two.
Only the marked slots are cleared and re-shot, so a guest redoing one bad
frame keeps the three good ones. `SessionState.photos` is therefore a
fixed-length array of optionals, one slot per shot, rather than a list that
grows as photographs arrive — a growing list cannot express "frame 3 is being
redone".

The ✕ in any title bar abandons the session and returns to attract. So does
90 seconds of no touching (configurable). Every touch anywhere resets that
timer, so nobody gets reset mid-decision.

## Printing

Everything above `PrinterService` is printer-agnostic. The flow hands over one
flattened `UIImage` plus a copy count and gets progress back.

**AirPrint (`AirPrintService`)** — the Canon SELPHY CP1500, and any thermal
printer that speaks AirPrint. `UIPrintInfo.outputType = .photo` is what makes
the SELPHY use its borderless postcard path.

**The booth prints silently.** The operator pairs a printer once in Admin;
after that `print(to:)` sends every job straight to it and no print sheet is
ever raised. If the paired printer is missing or unreachable the job fails to
the error screen — it does **not** fall back to the picker. A system sheet in
front of a guest is worse than a clear "tell the operator": they cannot fix a
network printer, and they can walk off leaving the iPad in a modal.

Copies: neither `UIPrintInfo` nor `UIPrintInteractionController` exposes a
copy count, so N copies is sent as N identical `printingItems`. That is the
only way to do a multi-copy job without putting the system print sheet in
front of a guest.

**Thermal (`ThermalSDKService`)** — generic ESC/POS over CoreBluetooth. It
scans for any peripheral with a writable characteristic, connects, and streams
`GS v 0` raster bands. This covers the common 58/80 mm Bluetooth modules
(Phomemo, Munbyn, Goojprt and the rebadges) because they all take the same
bytes. Images are Floyd–Steinberg dithered to 1-bit first: a thermal head is
one bit deep, and ordered dithering leaves a visible crosshatch on skin.

> **This is the one part built against an unconfirmed model.** See "Open
> questions" below.

## Layouts

`LayoutTemplate` is pure data — slots, margins, gutters, corner radius,
keyline, mat colour, footer height, footer columns, accent, and an optional
forced cell aspect. Adding a layout is adding a value to `LayoutTemplate.all`;
neither the renderer nor any print path learns about it.

Each slot carries a `source` — the index of the photograph that goes in it.
That one field is what makes duplicate strips possible: two slots pointing at
the same shot. `shotCount` is *derived* from the distinct sources, never
hand-written, because a slot list and a shot count that disagree is a bug
waiting to happen.

### The sheet design

The prints are dressed like a printed page, from the reference: monochrome
plates, a hairline rule, an oversized grotesk word set tight, a running sheet
number as `003.`, and micro caps tracked out underneath.

That dressing is data too. `decor` is a list of hairline rules and text runs
in unit space over the sheet, with `y` as a text **baseline** so type sits *on*
a rule the way it does in print. Text carries tokens — `{event}` `{caption}`
`{date}` `{word}` `{n}` `{shots}` — resolved at render.

`{word}` is the oversized display word (Admin › PRINT DESIGN › DISPLAY WORD,
falling back to the event name). It is deliberately **not** fitted: a long word
runs off the edge, and that overrun is the look. Everything else shrinks to
fit its box.

`{n}` is a real running count across the event, incremented only once a job
has actually been sent — a guest who backs out does not burn a number.

Photographs print monochrome because the type only reads against grey plates.
Admin › PHOTO TONE switches the whole booth back to colour.

Six ship, all offered to the guest:

| | shots | slots | |
|---|---|---|---|
| `1 SHOT / FULL BLEED` | 1 | 1 | edge to edge, no dressing |
| `1 SHOT / POLAROID` | 1 | 1 | white margin, deep foot |
| `2 SHOTS / STACKED` | 2 | 2 | two landscape frames + foot |
| `4 SHOTS / GRID` | 4 | 4 | 2×2 portrait on a warm mat |
| `4 SHOTS / DOUBLE STRIP` | 4 | **8** | two identical 2×6 strips on one 4×6 |
| `6 SHOTS / CONTACT SHEET` | 6 | 6 | 2×3 landscape |

The double strip is the classic: cut down the middle, two people each walk
away with one. `footerColumns: 2` puts a foot on each half, because each half
leaves on its own and needs the branding.

Every layout carries an `accent`. It bars the top of its tile, floods the tile
when chosen, and then follows the guest through the shot strip, the countdown
bar, the copy count and the print progress — so the colour picked on screen 1
is the colour of the whole session.

`cellAspect` holds cells at a true ratio whatever the paper does, which is
what keeps four portrait frames from becoming four squares on a different
media size. The capture screen draws that same aspect as a framing guide over
the live preview, so a group can see what the print will actually keep.

## Kiosk setup

- Landscape-locked, full screen, status bar hidden, idle timer disabled.
- Turn on **Guided Access** (Settings › Accessibility › Guided Access), then
  triple-click the top button on the attract screen to lock the iPad into the
  app. That is what disables the multitasking gestures and the home swipe.
- The operator console is **three taps in the top-left corner** of the attract
  screen, then a passcode (default `1234` — change it in the console).

## Storage

Photos are written to `Caches/PhotoboothSessions/<session>/` and the folder is
deleted when the session ends. Anything a crash left behind is swept on the
next session start. Nothing is uploaded anywhere.

## Open questions

These were called out in the brief. Where an answer was needed to finish the
work, a default was picked and is noted here — all four are one-line changes.

1. **Thermal printer make and model — still unanswered, and it matters.**
   The BLE ESC/POS path above is a real implementation, not a stub, but it is
   written blind. Three outcomes:
   - *AirPrint-capable* (Liene, some Munbyn): none of the Bluetooth code is
     needed. Set TARGET to AirPrint in Admin and pick a thermal paper size.
   - *Generic ESC/POS over BLE*: it should work as shipped. Pair it in Admin
     and print a test.
   - *Needs the vendor's own SDK*: `ThermalSDKService.swift` is the single
     file to replace. Nothing else in the app changes.
2. **Visual reference** — answered. Built to the plugin-panel reference:
   white paper, black ink, 4pt rules, bitmap type, muted pastel fills. All of
   it lives in `Panel/`. (The first build followed the brief's Y2K / Windows-98
   direction; that was replaced wholesale, not layered over.)
3. **Camera** — front by default (a guest has to see themselves), switchable
   in Admin. iPadOS has no useful path to an external USB webcam, so that
   option does not exist.
4. **Branding on prints** — built: event name, caption and date in the footer
   of any layout with one, set in Admin, off when the fields are empty. The
   1-shot layout is full bleed by design and carries no footer.
5. **Layout before or after capture** — before, as the brief's default.
